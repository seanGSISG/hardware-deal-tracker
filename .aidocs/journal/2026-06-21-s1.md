# Session 1 — Diagnose+fix poller tz crash (eBay 0/5000) + ship Activity log page

Sean reported the dashboard showed "eBay API 0 / 5,000 (0%)" despite the tracker
running ~24h, and asked: how often is it polled, what are the active sources, is
there a search log, and is eBay even working. Then asked for a dedicated Activity
page in the WebUI.

- **Root cause: the poller had been crashing on EVERY tick for ~24h** (eBay was
  never the problem). `get_items_due` compared `datetime.utcnow()` (naive) against
  `TrackedItem.last_searched`, which the Postgres `timestamptz` column returns
  **tz-aware** → `TypeError: can't subtract offset-naive and offset-aware datetimes`
  on poller.py:164, aborting the whole tick before any eBay call. Latent-by-design:
  the *first* cycle after a restart works (all items never-searched, no date math),
  stamps `last_searched`; from the *2nd* cycle on, reading those rows back poisons
  the tick. `record_call()` (poller.py:186) is never reached → redis budget key
  never created; its 24h TTL expired after that first cycle → WebUI reads 0/5000.
  - **Confirmed eBay itself works**: in-container OAuth + Browse search → token OK,
    274 live matches for "AMD EPYC 7543". Credentials valid.
  - **Fix** (`e908e4d`): `datetime.now(timezone.utc)` in `get_items_due` + coerce any
    naive `last_searched` to UTC before the interval compare + write tz-aware in
    `search_item`. Rebuilt/recreated backend; verified recovery: 18 items polled,
    1457 listings (1265 new), budget now `calls_today` incrementing.
  - Side effect of the backlog flush: 1265 new deals fired a notification storm that
    hit ntfy `429 Too Many Requests` (best-effort/caught, didn't break the poll).
- **Answered the diagnostic questions:**
  - **Cadence**: scheduler tick every 5 min (`POLL_SCHEDULER_INTERVAL=300`); per-item
    due intervals 5/10/20/30 min (5 build-critical CPUs+boards / 6 RAM / 12 storage /
    1 GPU). Bounded ≤10 never-searched + ≤20 due per cycle.
  - **Active sources**: **eBay only.** The 6 Shopify JSON-LD adapters are wired +
    per-store enabled but the global `ENABLE_SHOPIFY_SOURCES` flag is off in the live
    env; PCPartPicker is benchmark-only + disabled.
  - **Search log**: none existed — only Prometheus counters, ephemeral log lines, and
    result rows. That gap is what the new feature fills.
- **Shipped the Activity log feature** (`635bd18`):
  - `search_log` table (model + migration `search_log`, chained on
    `ntfy_notification_channel`) — one row per per-item search (`ok`/`skipped`/`error`)
    with source, found/new/dupes, calls_used, duration, detail. `tracked_item_id` is
    SET NULL on item delete + `item_name` denormalised so history survives deletion.
  - Poller writes a row at every return path of `search_item` (success/skip/error,
    error-path guarded against a poisoned session).
  - `GET /api/v1/activity` (paginated + status/source/item filters) + `/activity/summary`
    (last-search recency, 1h/24h counts, ok·skip·err, eBay calls/24h).
  - New `/activity` dashboard page: stat cards + status filter + 30s auto-refresh +
    paginated table, all dark-theme tokens; sidebar gains an "Activity" nav item.
  - Daily prune job (`search_log_prune_tick`, 04:30) enforces
    `SEARCH_LOG_RETENTION_DAYS` (default 14).
- **Verified**: migration applied (head=`search_log`); a live poll wrote 5 `ok` rows /
  5 calls; API summary+list+filter all 200 with real data via bearer token; frontend
  built clean (no `localhost:8001`, `.env` keeps `NEXT_PUBLIC_API_URL=/api/v1`), route
  built, unauth `/activity` correctly redirects to login. **Full suite: 352 passed, 6
  skipped.** Both commits unpushed (project convention).
- **Page**: https://deals.lab.lsdmt.me/activity (login admin/admin123).

### Lessons Learned
- **"0 of N (0%)" on an external-API meter is as likely a dead caller as a dead API** —
  the budget counter only moves when `record_call()` is reached, which sits *after* the
  upstream fetch. A crash anywhere earlier in the tick pins it at 0 and looks exactly
  like an API/auth failure. Check the poll-tick logs before suspecting the vendor.
- **`timestamptz` columns return tz-aware datetimes; `datetime.utcnow()` is naive** —
  any subtraction mixing the two raises and (when caught by an outer best-effort guard)
  silently halts the loop forever. Use `datetime.now(timezone.utc)` end-to-end and coerce
  on read. The repo's mock/test code still uses naive `utcnow()` (deprecation warnings) —
  a latent source of the same class of bug.
- **A latent crash can hide behind a successful first cycle** — "test under real conditions"
  means letting it run >1 poll cycle (and past the redis TTL), not just confirming the
  first tick/boot succeeds.
- **Adding a scheduler job breaks the exact-set assertion in `test_scheduler.py`** (like a
  migration breaks `test_single_linear_head`) — update the `{j.id ...}` set when adding a job.
