# Session 1 — Rescope watchlist to EPYC build (25 items) + retune polling

Sean asked to relax the seed hardware down to the EPYC build essentials. Cut the
36-item catalog to **25** scoped to the EPYC 7543P build, then spent the freed
eBay API budget tightening the build-critical parts.

- **Kept (25):** CPUs (7F72, 7543P), 3 SP3 boards (H12SSL-CT, H12SSL-i, ROMED8-2T),
  5 ECC RDIMM SKUs, the build's GPU slot (RTX PRO 6000 + RTX 6000 Ada + RTX PRO 4000
  as same-slot fallbacks), 6 U.2 NVMe, 6 HDD 16TB+.
- **Dropped (11):** inference GPUs L4/T4 (different purpose), 3 Mellanox ConnectX NICs,
  chassis/cooling/PSU (RM52, RM44, Eisbaer, HX1500i), 2 accessories (GPU bracket, rack rails).
  In the live DB this disabled 10 rows (T4 was already absent — DB had 35 not 36).
- **Retuned polling with the freed budget** (the real win — Sean was frustrated he
  couldn't catch a fair-priced 7543 + H12SSL-i):
  - Build-critical **CPU + all 3 boards → 5 min (P0 300s)**
  - **RAM stays 10 min** — does not move in 5 min (the s1-2026-06-19 budget lesson)
  - **U.2 + HDD → 20 min (P2 1200s)** "price watch" per Sean's framing
  - RTX PRO 6000 stays 30 min (too-new market, scam floor)
  - **~3,360 calls/day = 67%** of the 5,000 cap (was 93%), and **under the 4,000
    NEAR_LIMIT so nothing gets throttled** — P0 build parts always clear.
- **Source of truth + live state both updated**
  - `catalog.py` rewritten (25 items, 6 categories; PCPP_MAPPINGS + min_deal_score
    overrides + get_categories all pruned), seed regenerated (`seed_data_v2.sql`).
  - Live DB: applied seed (25 upserts, ON CONFLICT updates intervals) + disabled the
    10 out-of-scope rows via a catalog-derived `name NOT IN (...)` UPDATE (no typos).
  - Fixed 3 `test_catalog_pcpp_mapping.py` assertions (10-12 → 8 mapped; ConnectX-4
    null-check → P5510). Guard suite: **33 passed**.
  - Rebuilt + recreated `hdt-backend` so endpoints/reseeds match the new catalog.
- **Dependency-drift incident (caught + fixed)** — the rebuild 500'd on every request:
  `prometheus-fastapi-instrumentator 8.0.0` can't introspect FastAPI 0.138.0's
  `_IncludedRouter`. Root cause: the Dockerfile installs from `pyproject.toml` `>=`
  constraints and **ignores `uv.lock`** (pinned 0.136.3), so the rebuild pulled a
  newer FastAPI than the proven combo. Capped `fastapi<0.137` (`a0bde04`), rebuilt →
  `{"status":"healthy"}`, container `(healthy)`. Filed the reproducible-build root fix
  as an idea ([[build-reproducible-from-uv-lock]]).
- **Committed** `3f8557a` (catalog rescope, scoped to 3 files) + `a0bde04` (fastapi pin);
  left HANDOFF.md / plan / reports untracked from other work. **Not pushed** (project convention).

### Lessons Learned
- **The poller is DB-driven, not catalog-driven at runtime** — disabling items in
  `tracked_items` is what actually stops polling/alerts. The image rebuild only
  matters for the `/categories` + catalog-search endpoints and future reseeds.
- **Generate the `name NOT IN (...)` disable-SQL from the catalog itself** rather than
  hand-listing dropped names — derive the complement from the source of truth and you
  can't typo a SKU.
- The catalog has four pruning surfaces — ITEMS, `PCPP_MAPPINGS`,
  `_MIN_DEAL_SCORE_OVERRIDES`, and `get_categories` — a rescope must touch all four or
  the guard tests catch the drift.
- **An image rebuild is never free here** — the Dockerfile ignores `uv.lock`, so any
  rebuild re-resolves deps and can drift into a broken combo. Don't rebuild casually;
  the runtime poller is DB-driven and rarely needs it. "Test under real conditions"
  (hit `/api/v1/health`, wait for `(healthy)`) caught the 500 that a first-boot glance missed.
