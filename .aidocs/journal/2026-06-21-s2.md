# Session 2 — Ban-words filter (4542/7542) + China-origin flag on deals

**Problem:** Dashboard surfaced EPYC 4542 listings as "deals". Root cause:
eBay Browse `q=` is fuzzy, so the 7543P search (keywords "AMD EPYC 7543P …")
pulls back near-miss CPUs. The catalog only tracks 7543P/7F72 — the noise came
from the ingest layer, which had **no relevance filtering** at all.

- **Configurable banned-keyword stop-list** — new `BANNED_KEYWORDS` setting
  (`app/core/config.py`, default `["4542","7542"]`, env override accepts JSON or
  comma-separated via a `field_validator`). New pure helper
  `app/services/filters.py` (`title_is_banned`, `partition_banned`) does
  case-insensitive, **word-boundary** matching so "7542" never nukes a longer
  part number. Applied in `EbayPoller.search_item` to the combined eBay+Shopify
  `raw_listings` **before** dedup/persist/score → banned items are never stored
  or shown. Dropped count logged to `SearchLog.detail` ("banned-filtered: N")
  and returned as `banned_filtered`.
- **China-origin flag** — parser extracts `itemLocation.country`; added
  `item_country` (String(2)) + derived `is_china` columns to `Listing`
  (migration `2026_06_21_listing_origin`, head `search_log → listing_origin`).
  `CHINA_ORIGIN_CODES` config (default `["CN","HK"]`). Deals endpoint dumps the
  whole listing dict so the fields flow through automatically. Frontend: added
  `item_country`/`is_china` to `Deal` type and a 🇨🇳 chip on the deals page,
  dashboard top-5, and shared `ListingRow`. Mock client now emits a mix of
  US/CN/HK so the flag is exercised in dev.
- **Tests** — new `tests/test_banned_keywords.py` (filter + parser origin).
  Updated `test_community_migration` single-head assertion to `listing_origin`.
  Full suite: **357 passed, 6 skipped**. Frontend `tsc --noEmit` clean.

### Lessons Learned
- The catalog `keywords` field is only a *query seed*, not a relevance filter —
  eBay/Shopify fan-out needs a post-fetch title gate or fuzzy near-misses leak
  into the deal feed. The stop-list is the cheap global fix; a per-item
  "must-contain MPN/model" gate would be the stronger (future) version.
- Migrations auto-apply via the backend Dockerfile CMD (`alembic upgrade head`),
  so the new column lands on the next container restart — no manual DB step.
